# 取り込みパターン整理（複数素材・フォルダ・PDF/画像混在）

`docs/import-variations.md` の続き・発展として、1 ファイル（.zip 等）に複数の
フォルダ・複数 PDF・画像が混在するケースの**パターン整理と対応方針**をまとめる。
現時点の**検討メモ**（実装予定・未確定事項を含む）。

## 背景と目的

技術書典・BOOTH のダウンロードは「1 商品 = 1 ファイル」だが、その中身は
PDF 1 本のときもあれば、表紙画像 + 本文 PDF + オマケ画像の複合のときもある。
現行の取り込みは「PDF があれば最初の PDF だけ・残りはすべて無視」「PDF/EPUB が
無ければ全画像をパス順に 1 冊」という素朴な実装のため、複合素材で取りこぼしが起きる。

## 現行実装の挙動（`crates/core/src/import/mod.rs`）

- `import_zip_bytes`: 全エントリを読み、**最初の `.pdf` があれば PDF のみ取り込み**
  （画像・フォルダ・他 PDF はすべて無視）。次に `.epub`。無ければ
  **全画像（png/jpg/jpeg/webp/gif）をパス名順に 1 冊**として取り込む。
- フォルダの意味・表紙判定・重複判定・入れ子 zip は一切しない。

## 既知のパターン（現時点で観測・想定しているもの）

| # | パターン | 現行の扱い | 問題 |
|---|---|---|---|
| 1 | トップに画像のみ | 1 冊（パス順） | なし |
| 2 | トップに PDF のみ | 1 冊 | なし |
| 3 | 1 フォルダに画像 | 1 冊（パス順） | なし |
| 4 | 1 フォルダに PDF | 1 冊 | なし |
| 5 | トップに PDF、フォルダに画像 | **PDF だけ・画像を全無視** | 画像（表紙等）が消える |
| 6 | 複数フォルダに画像（内容すべて異なる） | 1 冊に結合 | 複数冊のはずが結合 |
| 7 | 複数フォルダに画像（文字あり/なしなどの差分） | 1 冊に結合（重複） | 重複ページ |
| 8 | トップに PDF と表紙・裏表紙画像（表紙裏表紙のみカラー） | **PDF だけ・表紙裏表紙を全無視** | 表紙が消える |
| 9 | トップに PDF と画像（画像が全部ある） | **PDF だけ・画像を全無視** | 写真版・別バージョンが消える |

→ **パターン 5 / 8 / 9 は「PDF-first, rest ignored」の実装で実質壊れている。**

## 追加でありそうなパターン（調査したもの）

### A. 複数 PDF（PDF-first の落とし穴）
- **A1.** PDF が複数（本文 + 別冊、前編/後編、表紙だけ PDF + 本文 PDF）
- **A2.** フォルダごとに PDF（各フォルダに PDF が 1 つ → フォルダ = 1 冊のはず）

### B. 圧縮の入れ子（nested archive）
- **B1.** ZIP の中に ZIP / 7z / rar（現行は内側 zip を image なし扱いで弾く）
- **B2.** 複数の圧縮ファイル同梱

### C. 表紙・付録の識別
- **C1.** 背表紙 / 帯 / 目次 / 奥付が画像として混在（「表紙だけ除外」だと漏れる）
- **C2.** 付録 / 特典 / 壁紙 / サンプル画像が複数（オマケをページに混ぜない）
- **C3.** 複数の「表紙っぽい」画像（どれが表紙か曖昧 → サイズ・アスペクト比・名前で推定）

### D. 同一内容の重複・差分
- **D1.** 文字あり/なしが PDF と画像に跨る（文字なし PDF + 文字あり画像）
- **D2.** 高解像/低解像の重複（同じページが 2 解像度）
- **D3.** カラー / モノクロの重複
- **D4.** 同名ファイルが複数フォルダに存在（重複）
- 判定には **perceptual hash（画像ハッシュ）or ファイルサイズ近似** が必要。

### E. ページ順・構成の不確定
- **E1.** ページ番号なし / ランダムなファイル名（連番抽出で整列）
- **E2.** 日本語ファイル名（`001.jpg` でなく `表紙.jpg` / `page1.jpg`）
- **E3.** 見開き（横長・縦長混在。1 枚 = 2 ページの判定）
- **E4.** ページ数不一致（PDF n ページ vs 画像 m 枚）

### F. 無視すべきファイル
- **F1.** サムネイル / プレビュー / 小さい画像（アイコン・バナー）
- **F2.** junk: `.DS_Store` / `Thumbs.db` / `__MACOSX` / 隠しファイル /
  `readme.txt` / ライセンス / 音声・動画（mp3/mp4）
- **F3.** 空フォルダ（現行は `is_dir` 無視済み）

### G. 形式・エラー耐性
- **G1.** HEIC / AVIF / BMP / TIFF / SVG（現在 `IMAGE_EXTENSIONS` に無い）
- **G2.** パスワード付き PDF / 暗号化 ZIP（開けずエラー → 明示 or 入力）
- **G3.** 壊れた画像 1 枚（現行は**全体エラー**。部分スキップにすべき）
- **G4.** 巨大画像 / 数百ページ（メモリ・処理時間。間引き or ストリーミング）

### H. メタデータ
- **H1.** PDF / EPUB メタデータからタイトル・作者を抽出（`books.author` が
  取り込み直後に空になる問題の改善にもつながる）

## 優先度（起きやすく・対応価値が高い順）

1. **複数 PDF / フォルダ = 1 冊の分割**（総集編・前編後編——よくある）
2. **表紙 / 付録 / オマケ / 無視ファイルの識別**
3. **文字あり/なしなど差分の判定**（最低限「同一内容の重複検出」）
4. **入れ子 zip の展開**
5. **ファイル名ヒューリスティック**（連番・表紙・見開き）
6. **壊れ画像の部分スキップ、対応拡張子の追加**

## 提案する実装方針（「自動推定 → 迷ったときだけ確認」に沿う）

1. **分類**: 各エントリを `表紙 / 本文 / 付録 / 無視` に分類
   （フォルダ名・ファイル名・サイズ・アスペクト比でヒューリスティック推定）
2. **グルーピング**: フォルダ単位 or 内容ハッシュ単位で「1 冊」を決める
3. **ページ整列**: 表紙 → 本文（連番・サイズ順）→ 裏表紙 → オマケ の順に統合。
   見開きは 1 ページ扱い（2 ページへ分割は任意）。
4. **判定**: 明確（PDF のみ / 画像のみ / 1 フォルダ）→ 自動取り込み /
   曖昧（複数候補・差分・複数冊）→ サマリー付き確認モーダル
5. **無視**: 明確に junk / サムネイル / 非対応ファイルは自動除外

## 進め方の候補

1. 分類・グルーピングの**ルール表を確定**する
2. 曖昧判定の境界（何を「迷う」とするか）を決める
3. TDD でパーサ + 分類ロジックを実装する

## ビューアのページ一覧（複数コンテンツ切替）

複数コンテンツ（複数 PDF / 画像 / フォルダ）があるとき、ビューア左上の
トップバー「ページ一覧」に**コンテンツの構造**を出して切り替えられるようにする案。
（features.md の TODO「1 ファイルに複数のフォルダ…」＝ 取り込み（import-patterns.md）の
**消費側**に当たる）

### 機能案

1. **構造表示**: 複数 PDF / 画像 / フォルダがあるとき、その構造（フォルダ → ファイル → ページ）をページ一覧に表示する。
2. **ファイル名 + 補足**: ファイル名・フォルダ名を表示し、括弧で型（PDF / 画像 / フォルダ）を補足する。
3. **優先表示ラジオ**: 表示時に優先的に出したいコンテンツをラジオボタンで選べる。
4. **優先外も選択可**: 優先表示以外でもページ一覧から選択して表示できる
   （→「どこまで読んだか」の管理が問題になる。下記「進捗の持ち方」参照）。
5. **名前をユーザ設定**: ファイル名だけだと分かりにくいので、ユーザが
   「表紙 / 裏表紙 / 本文 / 別冊」等の表示名を設定できる。

### ページ一覧の操作設計（確定 2026-09-06）

ページ一覧を「コンテンツ」ごとの**ドリルイン**にする。

```
ページ一覧（開いた状態）
├─ ◉ 本文.pdf (PDF)            >   ← 優先ラジオ + 名前・型 + 「>」
├─ ○ 別冊.pdf (PDF)            >
├─ ○ 表紙.png (画像)           >
└─ ○ 裏表紙.png (画像)         >
└─ メニューに戻る                    ← 最上位: トップバーのメニューへ

「>」or 行クリックで 1 つドリルイン
├─ [1][2][3][4]...[200]            ← そのコンテンツのサムネイル（従来グリッド）
└─ 上の階層に戻る                    ← コンテンツ一覧へ戻る
```

決定事項：

1. **行全体クリックで開く**: 「>」だけでなく行全体（優先ラジオ以外）をクリックしても、
   その行のコンテンツをドリルインする。「>」は明示的アフォーダンス。
2. **戻るは 1 つの切り替えボタン**: ラベルを階層で切り替える。
   最上位 = 「メニューに戻る」→ 読者トップバーへ。ドリルイン中 = 「上の階層に戻る」→ コンテンツ一覧へ。
   （ドリルイン中に「メニューに戻る」は出さない。2 段で戻れる）
3. **クリックでそのコンテンツを開く**: サムネイルをクリックすると、そのコンテンツを
   リーダーで開き、クリックしたページへ移動。**そのコンテンツの現在ページ**をハイライト
   （既読位置 = そのコンテンツの進捗。進捗のコンテンツ単位化と一致）。
4. **単一コンテンツは従来どおり**: コンテンツが 1 つなら「>」を省略してサムネイル
   グリッドを直接表示（現行 UX のまま）。複数コンテンツのときだけコンテンツ一覧 → ドリルイン。

### 前提（UI だけでは成立しない）

- **取り込み時に構造を保存していない**。現行リーダーは `documents::images_for_book()`
  のフラットなページ列（`pages/page_0001.webp`）しか持たず、フォルダ・ファイルの
  構造は取り込み時に消える。
  → 構造を出せるようにするには、**上記「提案する実装方針」の分類・グルーピング実装が先**。
  **保存先は DB を正**とする（`book_contents` テーブル + `document_images.content_id`）。
  Pack 側（`metadata.json`）には `contents` を書き出して**同期復元用**にする。

  **Pack が消えても復元できる**（DB を正にするから）:
  - **構造（どのページがどのコンテンツか）** = DB にある。`book_contents` を `backup.rs` の
    `TABLES` に追加し、`document_images`（既に対象済み）の `content_id` カラムと一緒に
    Drive の DB バックアップ JSON（`thundoku-backup.json`）に含めて復元する → **Pack が
    消えても構造は復元される**。
  - **ページ画像** = Pack（.opfspack）にしか無い。消えたら **Drive から再取得**する
    （Pack は `drive.sync.enabled` 連動で Drive にバックアップ済み）。`pack_entry_path`
    （Pack 内パス）が一致するので、構造と合わせてページを正しく再構成できる。

## 進捗の持ち方（読了ポリシー）

複数コンテンツだと「全体のページ数」が曖昧になるため、**読了（`finished_at`）と
進捗表示の基準**を以下のとおり定める。

### 読了の定義（推奨）

**「優先（メイン）コンテンツの最終ページ到達 = 読了」**

- 複数コンテンツのうち**優先表示に設定したコンテンツ = メインの本**を最後まで読んだら読了。
- **補助コンテンツ**（別冊・オマケ・表紙・裏表紙）は読了判定に**含めない**。
  - 例: 本文 200p + 別冊 50p → 別冊を読んでなくても「本文を最後まで読んだ = 読了」。
  - 逆転（別冊だけ読んで読了）は起きない。
- 優先表示ラジオ（上記機能 3）と**完全に噛み合う**（優先 = メイン = 読了基準）。
- **優先 = デフォルト表示のコンテンツ**（**取り込み時の確認ダイアログで決定**）。
  取り込み時に構造をまとめて確認するモーダルで、**「どのコンテンツをデフォルト表示（メイン）にするか」も
  同時に決める**（確認を 1 つに統合。初回表示の確認は出さない）。後からはページ一覧のラジオで変更可。
  - ここで選ぶのは**意味分類（本文）ではなく「デフォルト表示」**。選んだコンテンツが
    機能上の「本文/メイン」の役割を持つ（初期位置・カード進捗・読了判定の基準）。
  - 確認ダイアログの**初期選択 = 下記「デフォルト表示の決定」のヒューリスティック**
    （本文タイプと判定したコンテンツ）を提案。

### 進捗の持ち方（推奨）

**コンテンツごとに進捗を持つ**（`reading_progress` に `content_id` を追加して複合キー化）。

- コンテンツ A（本文）30 ページ、コンテンツ B（別冊）5 ページ、と**独立に保存**。
- コンテンツを開いたら**そのコンテンツの保存位置**へ。切り替えても別コンテンツの位置は失われない。
- 読了（`finished_at`）もコンテンツ単位。
- 既存データ（`content_id` NULL）=「優先 = 唯一のコンテンツ」扱いで互換。
- 本棚カードから本を開いたときは、**最後に読んだコンテンツ（最終閲覧）の保存位置**へ飛ぶ。
  （カード表示・読了判定は優先コンテンツ基準のまま。復帰先は「最後に読んだところ」）。
  各コンテンツを開くと、そのコンテンツの保存位置から再開する。

### 本棚カードの表示

- **単一コンテンツ**: 現行どおり「current / totalページ」+ 読了バッジ。
- **複数コンテンツ**: **優先コンテンツの「current / total」** を表示
  （total = メインのページ数。※「全ページ数」ではなく「メインのページ数」）。
  - 例: 本文 200p + 別冊 50p → カードは「120 / 200ページ」（別冊は含まない）。
  - （簡素案: 複数コンテンツ時は割合を消して「読了 / 未読」バッジのみ。）
- **カードは優先コンテンツの進捗のみ反映**。他コンテンツ（別冊・オマケ・表紙等）の
  進捗は**保持されるがカードには表示されない**。

### デフォルト表示の決定（取り込み時に確定）

「デフォルト表示（優先）にすべきコンテンツ」を決める。**取り込み時の構造確認モーダルに統合**する
（初回表示の別途確認は出さない）。
ここで選ぶのは**意味分類（本文）ではなく「デフォルト表示」**。選んだコンテンツが
機能上の「本文/メイン」の役割を持つ。
ヒューリスティックは**確認ダイアログの初期選択（候補）を提案**するためだけに使う。

なお **「本文」という型**（取り込み時の分類：表紙 / 本文 / 付録）は別概念で、
ページ整列・初期提案に使う（下記「提案する実装方針」の分類と一致）。

1. **ヒューリスティックで候補を自動選定**（確認ダイアログの初期選択用）。
   判定順（先に該当したものが勝ち）：
   - **名前で除外（表紙・付録類）**: ファイル名・フォルダ名に
     `表紙|cover|裏表紙|back|背表紙|おまけ|omake|特典|付録|サンプル|壁紙|サムネイル`
     を含む → 本文ではない（表紙 / 付録クラス）。
   - **名前で明示（本文）**: `本文|本編|honbun|main|body|text|正編` を含む → 本文。
   - **ページ数最多**: 上記で決まらない場合、**ページ数が最多**のコンテンツを本文。
     （PDF ならページ数、画像なら枚数。表紙・裏表紙は 1〜2 枚、付録は少ないので
     自然に本文が最多になる）。同数なら **PDF 優先**、さらに同数なら**パス順で先**。
2. **取り込み時の確認モーダルに統合**: 構造（グルーピング・ページ順）を確認するタイミングで、
   「**どのコンテンツをデフォルト表示（メイン）にしますか？**」を**ラジオで同時に選択**。
   **初期選択 = 上記ヒューリスティックの候補**。確定 → そのコンテンツを優先/メインに永続化。
   （初回表示時に改めて確認はしない）。
3. **後から変更可**: ページ一覧の優先ラジオでいつでも変更できる。

> 単一コンテンツなら確認不要（それが自明にメイン）。
> ヒューリスティックはあくまで「初期選択の提案」で、誤判定は確認モーダルで吸収される。

## 実装フェーズ（推奨順）

> 上記「優先度」は **import 側の対応優先順**。「実装フェーズ」は
> **import → リーダー → UI の end-to-end の作業順序**。両者は別物。

1. **import で構造を保存**（分類・グルーピング）→ `metadata.json` / `book_contents` に書き込み
2. **リーダー側**: `PackPageLoader` を「コンテンツ選択でページ列を返す」対応に
3. **ページ一覧 UI**: コンテンツツリー + 優先ラジオ + 選択切り替え（上記機能 1〜4）
4. **進捗をコンテンツ単位に**（マイグレーション + 本棚カードの表示基準。読了ポリシー適用）
5. **名前カスタム**（`display_name` 編集。機能 5）

> まず **1〜2（import 構造化 + loader）** を固めて **3（ページ一覧 UI）** を MVP に。
> ただし「どこまで読んだか」の完全対応（別冊等の位置保存・読了ポリシー）には
> **4（進捗のコンテンツ単位化）が必須**。3 の時点では構造表示 + 切替までで、
> 進捗は一時的に book レベル（別冊を開いても位置は保存されない）。
> 名前カスタム（5）は後追いでも動く。
