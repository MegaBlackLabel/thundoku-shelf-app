# 取り込みパターン整理（複数素材・フォルダ・PDF/画像混在）

`docs/import-variations.md` の続き・発展として、1 ファイル（.zip 等）に複数の
フォルダ・複数 PDF・画像が混在するケースの**パターン整理と対応方針**をまとめる。

**改訂 2026-09-10**: FANZA ライブラリ 290 件の**実データ**を API で調査し、旧版
（想定ベース）のパターン表を実測値で置き換えた。旧版からの変更点は §10 にまとめる。
「確定」と書かれた節以外は**検討中**（実装予定・未確定事項を含む）。

**同 2026-09-10 決定**: §11.1 の **D1〜D7 を確定**した。

- 総集編は **1 冊に畳む**（分冊しない）
- 形式もバリアントも **レンディションとして畳む**（1 コンテンツ + 切替）
- 表紙・裏表紙は **カバー画像のみ**（コンテンツにしない）
- 入れ子 zip は **1 階層だけ再帰**／壊れた画像は **部分スキップ**
- `folder-structures` API は **MVP では使わない**（取り込みは ZIP 解析を正）

### 0.1 ⚠ この API は ZIP の全量ではない（重要）

`d_305009`（ブレイクスルー-碧き七つの肉壺-FANZA同人ver_1.06）で検証:

| | 値 |
|---|---|
| API が返すファイル数 | **32**（`.txt` のみ） |
| 実際の ZIP エントリ数 | **5,398**（実ファイル 5,148 / 展開後 1,334.9MB） |
| 実際の中身 | nw.js ゲーム一式（`nw.dll` 136MB, `node.dll`, `icudtl.dat`, `.moc3`×71, `.efkefc`×120, `.pak`×56, `andapp-setup.exe` 86MB, `png`×51, `json`×1,948, `js`×179, `zip`×3 ほか） |

→ `folder-structures` は**「見せる用に curated されたビュー」**であって ZIP の目録ではない。
**取り込みの真実は常に ZIP 側**。API は

- ダウンロード前のプレビュー / 確認モーダルの材料
- Drive 復元時の構造の照合

には使えるが、**「この作品に画像は無い」の判断根拠にはできない**。

## 3. 設計の核: 「コンテンツ」と「形式」を分離する

### 3.1 なぜ必要か

実データの 113 件が「PDF と画像の両方」を持ち、うち **85 件はルートに PDF とフォルダを併せ持つ**。
**19 件は PDF 名とフォルダ名が完全一致**し（例: `藍染_モザイク修正.pdf` ↔ `藍染_モザイク修正/`）、
**40 件が形式名のフォルダ**（`jpg` / `png` / `PDF版` / `JPG版`）を持つ。

これは**同一内容の別形式**であって、別の本ではない。ここを分離しないと

- 同じ本を 2 回読む（進捗も読了も二重）
- 本棚カードの総ページ数が 2 倍になる

### 3.2 形式判定は名前で足りる（pHash は不要）

旧版は D2（重複検出）を「perceptual hash 必須・優先度 3」としていたが、実データでは
**決定的な名前規則だけで判定できる**:

1. **形式フォルダ名**: `jpg` / `jpeg` / `png` / `png版` / `pdf` / `PDF版` / `JPG版` / `画像(版)` / `カラー` など
2. **PDF 名 == フォルダ名**（拡張子を除いた完全一致）
3. **「文字あり」「文字なし」「カラー」「モノクロ」「モザイク修正」「黒棒修正」「SEあり」「SEなし」** は
   **同じコンテンツのバリアント**（形式と同じくレンディションとして畳む。決定 D3）

→ **pHash / 画像ハッシュは不要**。名前規則だけで **59 件**（PDF 同名 19 ∪ 形式フォルダ 40）が
機械的に判定できる。加えて 16 件が「文字あり/なし」等のバリアント名を持つ（決定 D3）。

### 3.3 データモデル（案）

```
book                （1 作品 = 1 pack = 1 冊。決定 D1: 分冊しない）
 └─ book_contents   読む単位（content_id, book_id, display_name, media_kind,
                     is_primary, sort_order）
     ├─ content_formats  レンディション（content_id, label, format_kind,
     │                   page_count, source_path, pack_entry_prefix, sort_order）
     └─ document_images  （content_id, format_kind, page_number, pack_entry_path, ...）
```

- `media_kind`: `image` / `pdf` / `audio` / `video` / `html`
- `content_formats` は**レンディション一覧**（切替可能な表示形態）。実データの裏付け:
  - 形式の違い: `PDF版` / `画像版`（40 件）
  - バリアントの違い: `文字あり` / `文字なし`、`モザイク修正` / `黒棒修正`（16 件）
  - 音声の違い: `MP3/SEあり` / `MP3/SEなし` / `WAV/SEあり` / `WAV/SEなし`
    （`d_297236` は **1 作品に 4 レンディション**が同居）
  - → コンテナ形式とバリアントを別軸にせず、**`label` 付きのフラットなリスト**にする
- レンディションを切り替えても**同じコンテンツ**として扱う（進捗・読了を共有。決定 D3）
- 表紙・裏表紙は `book_contents` に入れない（カバー画像として扱う。§7.4・決定 D4）

## 4. ページテキスト（`_export.txt`）— 画像のみ作品の救済

### 4.1 実データ

画像セット作品に `<<NPage>>` マーカー付きの**ページ別セリフ本文**が同梱される例がある。

```
<<1Page>>
壊れた姉弟と壊れる僕
この物語は、知人の話をもとに構成したフィクションです。
<<2Page>>
僕には好きな女性がいた
部活の先輩で同級生のお姉さん
```

**ページ番号と画像が 1 対 1 で対応する**（実測）:

| cid | 画像 | マーカー | 備考 |
|---|---:|---:|---|
| d_731200 壊れた姉弟と壊れる僕 | 64 | **64**（1..64 連番・欠番なし） | 完全一致 |
| d_271520 btid01jpg | 34 | **32**（1..32） | 画像 34 = 本文 32 + 表紙 `co` + サムネ `th` |
| d_408815 闇バイト_完成 | 19 | 15（2..18） | セリフの無いページは省略される |

本ライブラリでは 5 件（`_export.txt` を持つ作品）。

### 4.2 取り込み方針

- `_export.txt` をパースし `<<NPage>>` 単位で **`document_text` / `token_analysis` に投入**する
- 現行は画像セット取り込みで `texts: Vec::new()`（`import/mod.rs`）→ **タグ生成が何も得られない**
  - FANZA の画像のみ作品 164 件が該当
- これで**画像のみ作品でもタグ生成・全文検索が効く**ようになる
- ページ番号は `page_number`（1-indexed）にそのまま対応させる。表紙・サムネのぶんのずれは
  `_export.txt` のマーカー番号を正とする

### 4.3 「txt を画像として取り込む」の検討結果

**結論: 実装しない（需要が実質ゼロ・コストが見合わない）。**

実データ（290 件 / txt 74 ファイル / 31 作品）:

| txt の種類 | 件数 |
|---|---:|
| readme・はじめに | 13 |
| あとがき | 2 |
| メモ | 3 |
| タイルセット凡例（`Dungeon_A1.txt` 等） | 31 |
| その他（`_export.txt` 等） | 25 |

- **`.txt` は本物のテキスト**であることを実バイトで確認済み
  （`Dungeon_A1.txt` = UTF-8 BOM + `Water A|水場A / Deep Water|深い水場 …`、
  PNG/JPEG のマジックナンバーではない → 拡張子偽装ではない）
- **txt が本文の作品は存在しない**（txt のみ 2 件 = 1 件は nw.js ゲーム、1 件は空）
- したがって画像化しても「本として読む価値のあるページ」にならない

技術的な実現性（参考）:

| 方式 | コスト | 問題 |
|---|---|---|
| フォント描画（`ab_glyph` / `fontdue` + `image`） | 新規依存 1〜2 crate | **CJK フォントが必要**（同梱 ~5MB、OS フォント依存は Windows/macOS でパスが違い脆い） |
| シェーピング付き（`cosmic-text`） | 依存が重い（swash / rustybuzz / fontdb） | 上記 + ビルドサイズ |
| テキストのまま表示 | ビューアが画像前提なので UI 改修が必要 | ページ送り・ズームの作り直し |

→ 現行 `crates/core/Cargo.toml` にフォント系クレートは無い（`image` 0.25 / `webp` / `libwebp-sys`）。

**代替（推奨）**: §4.2 の `_export.txt` → `document_text` 投入。**フォント不要・依存追加なし・
ページ対応が実測で取れている**。テキストを「読む」必要が本当に出たら、ビューアに
テキストページ表示を足すほうが描画より安い。

非書籍（txt のみ / 0 ファイル）は **取り込み対象外**としてスキップ + 通知（§5.4）。

## 5. 分類・グルーピング規則

### 5.1 名前ヒューリスティック（実測付き）

旧版の正規表現をそのまま実データに当てた結果:

| 旧版の規則 | 発火 |

| 除外 `表紙\|cover\|裏表紙\|back\|背表紙\|おまけ\|omake\|特典\|付録\|サンプル\|壁紙\|サムネイル` | **9 / 290** |

**実データで観測された語彙（追加すべきもの）**:

| 用途 | 実在した名前 |
|---|---|
| 表紙/裏表紙 | `5.表紙`, `総集編表紙.jpg`, `benrionna_omote_re.jpg`, `benrionna_ura_re.jpg`, `btid01co.jpg` |
| サムネイル | `btid01th.jpg`, `thumb/` |

| 本文 | `本編／jpg`, `作品本体`, `本体`, `maindata` |

| バリアント | `文字あり`, `文字なし`, `モザイク修正`, `黒棒修正`, `旧…版`, `SEあり`, `SEなし` |
| セット | `2023販売用データ`, `01`〜`05`, `asobi`, `卒業式` |

**フォルダ名の数字接頭辞（`1.`, `2.`, `5.`）は作者の意図的な順序**なので、
`sort_order` の第一キーに使う。

### 5.2 無視するファイル

- `Thumbs.db`（実在・`type=ETC`, `ext=db`）/ `.DS_Store` / `__MACOSX` / `desktop.ini`
- `readme.txt` / `ご挨拶.txt` / `メモ.txt` / `あとがき.txt`（`_export.txt` を除く）
- ゲーム同梱物（`nw.dll`, `node.dll`, `icudtl.dat`, `.pak`, `.moc3`, `.efkefc`, `*.exe`, `*.js`, `*.json`）
- 空フォルダ（実在 1 件）

### 5.3 ファイル名エンコーディング

実 ZIP は **Shift-JIS** が主流（UTF-8 フラグ付きは一部）。
`import/mod.rs` は `zip` crate の `name()` を使っており、Shift-JIS 名は**文字化けしたまま
DB に入る**（実 DB に `âMâUÄòé┼é⌐éφéóéóùtÄqé│é±.pdf` が保存されているのを確認）。

→ **ZIP の生バイトを自前でデコードする必要がある**（UTF-8 フラグ → UTF-8、
無ければ CP932 / Shift-JIS）。`books.file_name`・タイトル・将来の表示名すべてに影響する。

### 5.4 非書籍の扱い

| 条件 | 扱い |
|---|---|
| 画像 / PDF / 音声 / 動画が 1 つも無い | 取り込み対象外。エラーではなく**スキップ + 通知** |
| ファイル 0 件 | 同上 |
| ゲーム / ソフト（`type` が `ETC` 主体 + 実行ファイル） | 同上（将来 `media_kind = software` で扱う余地） |

## 6. 優先（メイン）コンテンツの決定

### 6.1 手順（改訂案）

1. **レンディションを畳む**（§3.3）→ コンテンツ候補を確定。
   コンテンツの単位は**ページを直接含むフォルダ**（`総集編/1.話A/…` なら `1.話A`。
   実データ `d_614383` は 5 フォルダ）。形式フォルダ（`jpg` / `PDF版` / `画像`）と
   上位の入れ子フォルダは単位にしない。並び順はフォルダ名の自然順（`1.`〜`5.`）
2. カバー系（表紙・裏表紙・サムネイル）を**コンテンツ候補から外す**（§7.4。カバー画像に使う）
3. 名前で明示（本文/本編/本体/作品本体/maindata 等）→ 採用
4. 名前で除外（オマケ/特典/付録/`SEなし`/`文字なし`）
5. 残りは**内容単位のページ数最多**。同数なら PDF のレンディションを優先、次にパス順

### 6.2 ⚠ 「PDF ならページ数」は使えない

実データで **PDF のファイルサイズは全 123 件が `0B`**、ページ数は API に存在しない。
さらに `fileNum` は**ファイル数**なので、形式フォルダを畳まないと
`PDF版(1)` が `JPG版(244)` に負ける（中身は同じなのに）。

→ ページ数による比較は

- **画像 / 音声 / 動画**: `files.length` で可能
- **PDF**: ZIP を展開して `pdfium` / `mupdf` の `page_count()` を呼ぶまで不明
  （レンダリングは不要なので、ダウンロード後なら安価に取れる）

したがって「確認モーダルの初期選択」は **DL 前は名前 + ファイル数ベース**、
**DL 後はページ数で確定**、の 2 段構えにする。

### 6.3 取り込み時の確認モーダル

- 明確（形式が 1 つ・コンテンツが 1 つ）→ 自動取り込み + トーストで構成を明示
  （`import-variations.md` の方針を維持）
- 曖昧（形式が複数 / コンテンツが複数 / 差分セット）→ サマリー付きモーダルで
  「どのコンテンツをデフォルト表示（メイン）にするか」を**同時に**選ばせる
- **初期選択**は §6.1 のヒューリスティック。DL 前なら `folder-structures` でサマリーを作れる
  （§0）
- ✅ **実装済み（2026-09-11）**: core の `analyze_zip` / `commit_zip` 分割を使い、
  アプリは ZIP 取り込み時に計画を立て、**曖昧な構造（コンテンツが複数 / 形式が複数）の
  ときだけ**確認モーダルを出す。モーダルはコンテンツごとの要約
  （表示名・種別・`画像 48ファイル` など）を出し、**既定表示（メイン）を選ばせる**。
  初期選択は計画の既定（§6.1 のヒューリスティック）。
  「キャンセル」で取り込みを中止（ダウンロード済みデータは破棄）。
- 明快な構造（コンテンツ 1 つ・形式 1 つ）は従来どおり自動取り込み + トースト
- Drive から降ってくる pack はモーダルを出せないため、
  「迷う構造の pack は既定の優先で取り込み、後からページ一覧で変更（名前も変更可）」が既定動作

## 7. ビューアのページ一覧（複数コンテンツ切替）— 確定設計

複数コンテンツ（複数 PDF / 画像 / フォルダ / 形式）があるとき、ビューア左上の
トップバー「ページ一覧」に構造を出して切り替える。

### 7.1 ページ一覧の操作設計（2026-09-11 改訂）

**トップバーのメニューに「形式（レンディション）ごとの行」を出し、それを選ぶとその形式の
ページ一覧（サムネイル）を開く。** 切替はメニュー側に集約し、ページ一覧パネルは
サムネイルだけにする（実装に合わせて 2026-09-06 案から変更）。

```
トップバー（開いた状態）
├─ 📁 1.尻穴便女    画像 48ファイル        ✓ 表示中   [一覧 ›]   ← 行クリックで切替
├─ 📁 2.尻穴便女 痒 画像 53ファイル                  [一覧 ›]
├─ 📄 姉とアナルセックスする話.pdf  PDF 16ページ ✓ 表示中 [一覧 ›]
├─ ショートカット                                              ›
└─ 自動再生設定                                                ›

ページ一覧（「一覧 ›」を押した形式）
├─ [1][2][3][4]...[200]                          ← その形式のサムネイル
└─ ← メニューに戻る
```

決定事項:

1. **切替行はトップバーのメニューに出す**: 従来の「ページ一覧」1 行の位置に、
   形式ごとの行を並べる。**レンディションが 1 つだけの本でも 1 行出す**
   （`PDF` だけの本 → `PDF` 行）。コンテンツ情報を持たない旧データの本だけ
   「ページ一覧」行にフォールバックする。
2. **行の構成**: アイコン（画像 = フォルダ / PDF・EPUB = ドキュメント）+ 名前 + 種別の補足。
   名前は**コンテンツ名だけ**（`本文` や旧データのように名前が無いときだけレンディション名
   `JPEG` / `PDF`）。同じ内容に複数の形式があっても形式名は付けない（区別はアイコンと
   補足で分かる）。補足は `画像 48ファイル` / `PDF 16ページ`。右端に「一覧 ›」ボタンを置く。
3. **行クリック = 切替**: 選んだコンテンツ／レンディションを表示し、**そのコンテンツを
   既定表示（`is_primary`）にする**（ラジオボタンは置かない）。
   現在表示中の行には緑のチェック + 「表示中」を出す。
4. **「一覧 ›」= その形式のページ一覧（サムネイル）を開く**。
5. **戻るは 1 つ**: ページ一覧の「← メニューに戻る」でトップバーのメニューへ。
6. **表紙・裏表紙は行に出さない**（決定 D4。カバー画像として扱う → §7.4）。
   ※ 2026-09-06 の確定案では「表紙.png / 裏表紙.png」を 1 行ずつ出す想定だったが、
   決定 D4 でカバー扱いに変更した。

### 7.2 実データからの追加（改訂）

5. **形式・バリアントはコンテンツではなく「レンディション切替」**（決定 D3）:
   `PDF版` / `画像版`、`文字あり` / `文字なし`、`MP3/WAV` × `SEあり` / `SEなし` は行を分けず、
   1 行の中にレンディションセレクタを出す。実データでは 85 件が PDF とフォルダを
   併せ持ち、59 件が名前規則で形式違いと判定でき、16 件がバリアント名を持つため必須。
6. **同階層に大量のコンテンツがある場合**（`d_475465` = 53 フォルダ / 3,321 ファイル）でも
   破綻しないよう、ページ一覧とサムネイルは**遅延読み込み**を前提にする。
   ✅ **実装済み（2026-09-11 / §11.2 R6）**: 行単位の仮想化 + 可視行のみ読み込み +
   サムネイルの縮小保持（200px・上限 120 枚）。旧実装は開いた時点で全ページの
   フル解像度画像（1 枚約 45MB）を読んでいた。

### 7.3 前提（保存先・復元）

- **保存先は DB を正**とする（`book_contents` + `content_formats` + `document_images.content_id`）
- Pack 側（`metadata.json`）には `contents` を書き出して**同期復元用**にする
  - 現行 `metadata.json` は `schemaVersion` / `title` / `author` / `circleName` /
    `purchaseDate` / `readingProgress` のみ
- **Pack が消えても構造は復元できる**:
  - DB バックアップ（`backup.rs` の `TABLES`）に `book_contents` / `content_formats` を追加
  - ✅ **Pack 復元は取り込み状態まで再構築する（2026-09-11 実装）**:
    `import::rebuild_from_pack` が pack の `metadata.json`（`contents`）とエントリから
    `book_contents` / `content_formats` / `imported_documents` / `document_images` を作り直す。
    すでに取り込み済みの本は何もしない（ローカルの取り込みを壊さない）。
    ページ画像の寸法はエントリのヘッダから読む（画素デコードはしない）
  - 進捗（`reading_progress`）は DB バックアップ（`thundoku-backup.json`）から復元される
  - FANZA 作品は `folder-structures` API で構造を再取得できる（§0）が、**ページ画像は Pack が必要**
- 旧 Pack（`contents` なし）は「全ページ = 単一コンテンツ」にフォールバック

### 7.4 カバー（表紙・裏表紙）の扱い（決定 D4）

**表紙・裏表紙はコンテンツにせず、カバー画像として扱う。**

- 実データ: ルートに PDF + 画像の 22 件のうち 4 件が `omote` / `ura` / 表紙系の名前
  （`benrionna_omote_re.jpg` / `benrionna_ura_re.jpg` 等）。`5.表紙` フォルダ（2 枚）の形も実在
- 既存実装と同じ流儀: pack の `thumbnail.webp` → `cover.webp` を順に読んでカード画像を作る
  （`bookshelf.rs`）。PDF 取り込みでは既に両方を生成している
- 画像セット取り込みは `thumbnail.webp` しか生成していないため、
  **表紙画像がある場合は `cover.webp` として pack に入れる**よう揃える
  （無い場合は先頭ページを `thumbnail.webp` に使う現行動作のまま）
- ページ一覧・進捗・読了の対象外（読了判定にも影響しない）

## 8. 進捗・読了ポリシー

### 8.1 読了の定義

**「優先（メイン）コンテンツの最終ページ到達 = 読了」**

- 複数コンテンツのうち**優先表示に設定したコンテンツ**を最後まで読んだら読了
- **補助コンテンツ**（別冊・オマケ・付録）は読了判定に**含めない**。
  表紙・裏表紙はコンテンツではないため（決定 D4 / §7.4）そもそも読了の対象外
- 例: 本文 200p + 別冊 50p → 別冊を読んでなくても読了。逆転（別冊だけ読んで読了）は起きない

### 8.2 進捗の持ち方

- **コンテンツ単位**で持つ（`reading_progress` に `content_id` を追加して複合キー化）
- ⚠ `reading_progress` は `book_id TEXT PRIMARY KEY`。SQLite は PK 変更に
  `ALTER TABLE` が使えないため**テーブル再作成 + データ移行**が必要
- ⚠ `backup.rs` の PK 一覧（`"reading_progress" => &["book_id"]`）と
  WHERE 句（`book_id IN (...)`）も同時に直す
- **レンディション違い（PDF 版 / 画像版 / 文字あり / 文字なし 等）は進捗を共有する**
  （同一コンテンツのため。決定 D3）
- ⚠ **`progress::upsert` は `finished_at` を一度設定すると二度と消さない**。
  優先コンテンツを後から変更すると**誤った読了バッジが残る**ため、
  優先変更時に再評価が必要だった。
  ✅ **行が分かれたことで自然に満たされる（2026-09-11 検証）**: カード・統計が見るのは
  優先コンテンツの行だけなので、優先を別冊へ変えると読了バッジは消え、本編の読了は残る
  （`progress::tests::changing_the_primary_content_does_not_keep_a_wrong_finished_flag`）

### 8.3 ページ毎の閲覧記録

`page_views` は `PRIMARY KEY (book_id, page_number)`、`document_text` /
`token_analysis` も `page_number` 単位。**コンテンツを跨ぐとページ番号が衝突する**
（本文 1 ページ目と別冊 1 ページ目が同じ行に合算される）。

→ `page_views` / `document_text` / `token_analysis` **すべてに `content_id` を追加**する。
`document_text` / `token_analysis` は §4 の `_export.txt` 投入先でもあるため必須。

### 8.4 本棚カード

- **単一コンテンツ**: 現行どおり「current / total ページ」+ 読了バッジ
- **複数コンテンツ**: **優先コンテンツの**「current / total」を表示
  （total = メインのページ数。全ページ数ではない）
- カードは優先コンテンツの進捗のみ反映。他コンテンツの進捗は保持されるがカードには出さない
- ⚠ カードは「優先コンテンツ基準」、復帰先は「最後に読んだコンテンツ」なので、
  ユーザーには「120 / 200 なのに開いたら別冊 5 ページ」に見える。
  優先外を読書中は「別冊を読書中」等のバッジで緩和する

## 9. 実装フェーズ（推奨順）

> §2 の「パターン」は**分類**、ここは **import → リーダー → UI の end-to-end の作業順序**。

1. **import の下地を直す**（コンテンツ分割の前に必須）
   - `import_zip_bytes` → パイプラインを `analyze` / `confirm` / `commit` に分割
   - ファイル名の **CP932 / Shift-JIS デコード**（§5.3）
   - `_export.txt` → `document_text` 投入（§4.2）
   - junk / 非書籍の除外とスキップ通知（§5.2 / §5.4）
   - `.bmp` など画像拡張子の追加、壊れた画像の部分スキップ
   - `import_zip_bytes` の PDF / EPUB 分岐で **`reuse_book_id` が落ちているバグ**修正
     （未ログインの再ダウンロードで重複本ができる）
2. **import で構造を保存**: 分類・グルーピング → `book_contents` / `content_formats` /
   `document_images.content_id` + `metadata.json` に `contents`
3. **リーダー**: `PackPageLoader` を「コンテンツ + レンディションの選択でページ列を返す」対応に
4. **ページ一覧 UI**: コンテンツツリー + 優先ラジオ + レンディションセレクタ + 遅延読み込み（§7）
5. **進捗をコンテンツ単位に**: テーブル再作成 + 本棚カード（§8）
6. **Drive 復元**: `import_book` を `document_images` / `reading_progress` まで再構築する
7. **名前カスタム**（`display_name` 編集）✓ 実装済み（2026-09-11）

> まず 1〜3 を固めて 4 を MVP に。進捗の完全対応には 5 が必須。

## 11. 決定事項と残件

### 11.1 決定（2026-09-10）

| # | 論点 | 決定 | 根拠 |
|---|---|---|---|
| **D1** | 総集編（1 ファイルに複数冊）の扱い | **1 冊に畳む**（1 商品 = 1 book = N コンテンツ）。分冊しない | `books.opfs_path` は UNIQUE、`books::find_by_source` / `resolve_reuse_id` は `(site_id, tbf_product_id) → 1 book` 前提。分冊すると再ダウンロードの重複抑止・`owner_sub` 紐付け・Drive の `{pack_id}.opfspack` 命名を作り直す必要がある |
| **D2** | 表紙 / 本文 / 別冊 | **切替コンテンツ**（1 ページ列に統合しない） | 総集編・別冊が実在。統合するとページ番号と進捗の基準が崩れる（§7） |
| **D3** | 「文字あり/なし」「モザイク/黒棒修正」「SEあり/なし」 | **レンディションとして畳む**（1 コンテンツ + 切替） | `d_297236` は MP3/WAV × SEあり/なし の **4 レンディションが 1 作品**に同居。文字あり/なしはページ数も同一。進捗・読了を共有するのが正しい（§3.3） |
| **D4** | 表紙・裏表紙 | **カバー画像のみ。コンテンツにしない** | 既存の `thumbnail.webp` → `cover.webp` の流儀と一致（`bookshelf.rs` がこの順で読む）。ページ一覧が短くなる（§7.4） |
| **D5** | 入れ子アーカイブ（B1/B2） | **1 階層だけ再帰展開**。深さ・展開後サイズ・エントリ数に上限、超過は無視 + 通知 | 実 ZIP に `zip` エントリが 3 つ存在する例を確認（`d_305009`）。構造 API では事前判定できない（§0.1） |
| **D6** | 壊れた画像（G3） | **部分スキップ + 警告**（1 枚で全体を失敗させない） | 現行は `image::load_from_memory(...)?` で全体エラーになる |
| **D7** | `folder-structures` API をアプリ本体で使うか | **MVP では使わない**。取り込みは ZIP 解析を正とする | 確認モーダルは DL 後（メモリ上の bytes）に出す設計で ZIP 解析で足りる。かつ API は ZIP 全量ではない（§0.1）ため真実の源にできない |

### 11.2 残件（2026-09-11 対応）

- **R1. 入れ子アーカイブ（D5）の上限値** — ✅ **実装済み**
  - 上限値: `MAX_NESTED_DEPTH = 1`（実データで確認できた入れ子は `d_305009` の 1 階層のみ）/
    `MAX_NESTED_BYTES = 512 MiB`（入れ子合計の非圧縮サイズ。解凍爆弾を弾く）/
    `MAX_NESTED_ENTRIES = 2000`（1 冊のページ数として十分大きく、異常アーカイブを弾ける）
  - 外側 ZIP 直下の `.zip` だけを 1 階層展開し、内側エントリ名を
    「入れ子 ZIP パス（拡張子除去）/内側名」に前置して通常のエントリとして合流させる
    （分類・グルーピング・pack 書き出しはそのまま効く）
  - 上限超過・壊れた入れ子は `warnings` に積んでスキップ（取り込み全体は失敗させない）。
    入れ子の中の `.zip` は展開せず深さ制限の警告
- **R2. `media_kind = html`（同人ソフト・HTML 閲覧型）の見せ方** — **対象外と確定**（実在 1 件
  `d_115794`）。ビューアが画像前提のため取り込まず、「取り込めるコンテンツがありません
  （txt のみ・ゲーム・HTML 閲覧型など）」と通知する（R3 の文言に含めた）
- **R3. 非書籍の通知文言と再取り込みの導線** — ✅ **実装済み**
  - `ImportError::NotAReadableWork`（読めるコンテンツが無い）を追加し、アプリで型により出し分け
  - 文言: 「取り込めるコンテンツがありません（txt のみ・ゲーム・HTML 閲覧型など）。
    この作品はビューアーで読めません」
  - 一部を読み飛ばしたとき（壊れた画像・入れ子上限など）はトーストに件数と先頭 2 件を出す
  - 再取り込みは既存のカードのコンテキストメニュー「再取得」
- **R4. 複数コンテンツ時の本棚カードの見せ方** — **追加対応しないと決定**
  - カードは優先コンテンツの進捗のみ（§8.4 の本体）で確定。**「別冊を読書中」バッジは不要**
- **R5. `_export.txt` の取り込み** — **現状維持と決定**（常に ON。設定化しない）
- **R6. 超肥大作品の初回取り込み時間とサムネイル生成** — ✅ **調査 + 実装済み**
  - 実測（release、1 ページ 2000x3000）: 取り込み = decode 55ms + **webp 再圧縮 749ms** +
    サムネ 29ms ≒ **834ms/ページ**。ページ一覧（旧実装）= 全ページを**フル解像度**で読み込み、
    1 ページ RGBA **約 45MB** → 192 ページで **約 8.7GB**
  - 対策 1: ページ一覧を**行単位で仮想化**し、サムネイルは**可視行だけ**読む。
    サムネイルは 200px に縮小して保持し、保持数に上限（120 枚 ≒ 24MB）を設けて古い順に捨てる
  - 対策 2: 取り込みのページ変換（デコード + webp 再圧縮）を**チャンク + 並列**化
    （ワーカーは `min(コア数, 8)`、順序は保持）→ 実測 **834ms → 211ms/ページ（約 4 倍）**。
    3,321 ページ換算で **44.5 分 → 11.7 分**（192 ページ本は 2.6 分 → 約 40 秒）
  - ⚠ 残る制約: **スクロール表示モードは全ページを読み込む**（開いた時点で全ページ分の
    フル解像度を保持）。数千ページ作品をスクロールモードで開くとメモリを大きく食うため、
    必要になったら同じ考え方（可視範囲のみ + 破棄）で対応する
